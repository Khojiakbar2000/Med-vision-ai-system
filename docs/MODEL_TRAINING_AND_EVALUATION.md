## M2 — repeatable multi-case evaluation

Implementation is in `backend/medvision_ai/research.py`; invocation is `npm run ai:evaluate -- --manifest <manifest.json> --output <results.json> [--device auto|cpu|mps|cuda]`. It accepts an explicit manifest and never scans a directory. The manifest must live outside the repository with the research data; use external absolute paths in it. Each case can declare either:

1. Four explicit `modalities` paths keyed exactly `t1c`, `t1`, `t2`, `flair`; or
2. One four-channel MSD Task01 `image` with the explicit `imageChannelOrder` `[`"flair"`, `"t1"`, `"t1c"`, `"t2"`]` plus its `reference` path.

Example schema (replace these placeholders with authorized local research files; none are included):

```json
{
  "schema": "medvision-evaluation-v1",
  "dataset": {
    "name": "Dataset name",
    "version": "Release/version",
    "license": "License identifier",
    "source": "https://canonical-dataset-documentation.example/",
    "referenceConvention": "msd_task01",
    "independenceAssessment": "potentially overlapping; patient-level provenance not verified",
    "useForTraining": false,
    "heldOutEvaluationExcluded": false
  },
  "cases": [
    {
      "image": "/external/research-data/case-image.nii.gz",
      "imageChannelOrder": ["flair", "t1", "t1c", "t2"],
      "reference": "/external/research-data/case-label.nii.gz"
    }
  ]
}
```

The loader converts orientations to nearest canonical RAS without interpolating, validates the exact grid and 1 mm spacing through the existing protocol, checks reference affine/shape and supported labels before inference, and retains the original reference values. MSD channel order is explicitly reordered to T1c/T1/T2/FLAIR. Per-case data errors remain in output as a fixed error code; a failed case is never silently dropped. Model-load failure yields a failed record for each manifest entry. Results are written as both JSON and CSV with ordinal aliases only (`case_000001`, …), per-case WT/TC/ET Dice, IoU and HD95, inference time, prediction and reference volumes, aggregate mean/median/sample standard deviation/min/max, case counts, model/checkpoint provenance, preprocessing, dataset description, CPU fallback, and process/device memory when measurable. No source path, source file name, or supplied case/patient ID is copied to the output. The process peak RSS is cumulative for the CLI process, not a per-case attribution.

The optional device selector returns a clear unavailable-device error for explicit MPS/CUDA requests. `auto` selects CUDA, then MPS, then CPU. If accelerated model initialization or inference fails, evaluation reloads the same checksum-verified checkpoint on CPU and records that fallback; `--no-cpu-fallback` disables it. Device visibility is not a support guarantee: an actual inference must succeed before a backend is reported as validated.

## M3 — dataset independence assessment

The available evaluated cohort is the Medical Segmentation Decathlon Task01 Brain Tumour set, licensed CC BY-SA 4.0 in the AWS Open Data Registry. The original MSD paper states the brain dataset contains the same cases as the BraTS 2016 and 2017 challenges. The pinned MONAI checkpoint metadata says it trained on BraTS 2018. These sources do not establish a case-level overlap map between the MSD training sample used here and the bundle's training cohort, nor do they establish independence. This is therefore **potentially overlapping and not independent validation**. No re-identification or patient-ID matching was attempted. No second cohort or multi-case dataset was downloaded; the free-space constraint and user's approval boundary are respected.

For new evaluations, dataset manifests must record the release, license, source, reference convention, and overlap assessment. A dataset should be called independent only when the dataset owners' provenance or a documented, privacy-preserving patient-level exclusion establishes separation from all MONAI training/validation data. A later BraTS release by itself is insufficient proof.

## M5–M7 — fine-tuning, tracking, and paired comparison

`backend/medvision_ai/training.py` reuses the exact checkpoint-loaded SegResNet and its nonzero per-channel normalizer. Its defaults follow the official MONAI bundle `train.json`: 300 maximum epochs, Adam at 1e-4, weight decay 1e-5, squared sigmoid Dice loss, cosine annealing, batch size 1, 224×224×144 random crops, three spatial flips, intensity scale/shift augmentation, per-epoch validation, and CUDA mixed precision when CUDA is available. CPU and MPS stay full precision. Patient groups are split deterministically from a seed, or declared `train`/`validation` partitions are honored; mixed patient partitions and any explicit `test`/`heldout`/`evaluation` partition are rejected. The manifest must also explicitly declare `dataset.useForTraining: true` and `dataset.heldOutEvaluationExcluded: true`. The user remains responsible for ensuring the training manifest contains no final-evaluation patient, because the software cannot infer data-sharing history from a local manifest.

Fine-tuning is opt-in: `npm run ai:train -- --manifest <training-manifest.json> --output-dir <new-experiment-dir> [--device auto|cpu|mps|cuda]`. A training manifest must explicitly set both `useForTraining` and `heldOutEvaluationExcluded` to `true`; the evaluation example above is deliberately marked false. It never writes to the baseline checkpoint or to a non-empty experiment directory. `best.pt`, resumable `last.pt` (model/optimizer/scheduler/scaler/epoch and random-generator states), `metadata.json`, and append-only local `metrics.csv` are written to the requested external experiment folder. The metadata records the base SHA-256, best-checkpoint SHA-256, training configuration, seed, data provenance, software versions, device, runtime, memory, and validation history. Resume only from that experiment's `last.pt`. A split, config, target-label conversion, model hash validation, and data loader are unit tested; no training was executed because the available case count is one and no multi-case training manifest was approved/provided.

Use the same ordered held-out manifest for baseline and candidate runs. Candidate evaluation uses `--experiment-metadata <experiment/metadata.json>` together with `--weights <experiment/best.pt>`; both candidate and original checkpoint hashes are checked. `npm run ai:compare -- --baseline <baseline-results.json> --candidate <candidate-results.json> --output <comparison.json>` reports paired per-case deltas for WT/TC/ET Dice and IoU, inference time, device memory when available, and failed/unpaired cases; process peak RSS is reported per run. Its pairing key is the ordinal manifest position, so both evaluation files must come from the exact same manifest in the same order. It does not assert a candidate is better. The original baseline remains the viewer default.

No MLflow or database was introduced. Experiment artifacts stay local; no metrics are uploaded. The training CLI is an operator tool and is not exposed in the standard viewer.

## Phase 5.1 — BraTS access and data audit — 2026-11-13

Its tasks include brain metastasis segmentation and glioma histopathology, so registration to that challenge does not itself establish permission to use BraTS2024 GLI data ([challenge overview](https://challenges.synapse.org/Challenges/DetailsPage/Overview?id=syn74274097)). The signed-in browser session was not exposed to this workspace; no Synapse credentials or tokens were read. I could not verify the account's team membership or data permissions.

The best modality/annotation match for a future transfer experiment is **BraTS2024 adult glioma post-treatment (GLI), v2**: T1, T1-Gd, T2, and FLAIR with expert-reviewed segmentation, registered to the MNI atlas. The official challenge announcement says validation files are available to members of the BraTS2024 Data Access team, but their labels remain private; the challenge wiki describes the training and validation access process ([validation release and access requirement](https://www.synapse.org/Synapse:syn53708249/discussion/threadId=11237), [challenge data description](https://www.synapse.org/Synapse:syn53708249/wiki/626323)). The data-use terms govern the dataset; the research paper's license must not be treated as a dataset license.

BraTS2024 GLI label values are 0 background, 1 NETC, 2 SNFH, 3 ET, and 4 resection cavity. For WT/TC/ET comparison, use WT={1,2,3}, TC={1,3}, ET={3}; cavity is its own class and is excluded from these regions. The evaluation and training code now has the explicit `brats_2024_gli_post_treatment` convention. It maps the pretrained model's enhancing output to GLI label 3 and does not count label 4 as tumor. This mapping has synthetic regression coverage; no BraTS data has yet passed this application's loader.

The organizer's changelog identifies the corrected v2 GLI archive and recommends using the consistent full release rather than mixing corrected individual files ([official GLI data changelog](https://www.synapse.org/Synapse:syn53708249/discussion/threadId=11204)). The challenge distribution is an archive; no official 5–10-case package was found. A participant reported a 34.9 GB training download, which is an estimate rather than authoritative file metadata. Synapse's web download cart allows at most 5 GB or 100 files per package ([Synapse UI download limits](https://docs.synapse.org/synapse-docs/downloading-data-from-the-synapse-ui)). No download was started: a full archive is outside the previously scoped small pilot and requires separate approval. ### Synapse ZIP retrieval

Synapse officially supports whole-file retrieval through its Python, R, and CLI clients (`synapse get`) and caches completed files by checksum ([programmatic download documentation](https://docs.synapse.org/synapse-docs/downloading-data-programmatically)). The documented client does not offer selective extraction from a ZIP entity, and its documentation does not promise resumption of interrupted partial files. Synapse also documents temporary AWS STS access for Synapse storage only where an STS storage location has been configured; that is a storage-access feature, not a managed GPU service ([Synapse STS/direct storage documentation](https://docs.synapse.org/synapse-docs/compute-directly-on-data-in-synapse-or-s3)).

For a single ordinary ZIP object, selective extraction is technically possible if the authorized download URL accepts byte-range requests: read the ZIP64/central-directory data from the end of the archive, then range-read the compressed extents for each selected modality and mask. Amazon S3 supports `Range` on `GetObject` ([AWS range-download documentation](https://docs.aws.amazon.com/AmazonS3/latest/API/API_GetObject.html)). That is an inference about the object-store mechanism, not proof that the protected BraTS2024 Synapse entity exposes a compatible signed URL or preserves the Range header. I attempted metadata/one-byte probes against Synapse and TCIA, but the network requests from this environment returned a connection failure; no authenticated browser surface or Synapse CLI/client is available here. Thus `206 Partial Content`, authenticated range access to the BraTS2024 archive, the archive's ZIP64 layout, and individual-entry extraction remain **unverified**. No full or partial archive was downloaded. Do not treat S3's general capability as a verified Synapse guarantee.
